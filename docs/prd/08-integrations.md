# 8. Integrations

## Claude Code

`lastro setup claude` installs the three pieces at once:

- **MCP server** in the project's `.mcp.json` (see [Interfaces](07-interfaces.md)).
- **Hooks** in the project's `.claude/settings.json` (see [Making the agent comply](06-enforcement.md)).
- **Marked section** in `CLAUDE.md`.

It also ships as a **Claude Code plugin**, with hooks, MCP and skills together:

| Skill | What it is for |
|---|---|
| `/lastro:intake` | Registers the source, breaks it into atomic requirements with literal quotes and lists what was left open |
| `/lastro:spec` | Fills in a package's required fields and turns doubts into questions or decisions |
| `/lastro:build` | Takes the next `approved` requirement, implements it, links the tests and runs `lastro_verify` until it passes |
| `/lastro:report` | Generates the package report for the requester |
| `/lastro:triage` | Takes a complaint, records the incident and proposes triage, cause and billing |

## Claude Ship

Claude Ship takes care of the pull request: **Code Review** reviews it, **PR Steward** fixes broken CI, conflicts and comments, and **Claude Approvals** applies the team's approval policy. It starts once the code already exists and doesn't know what the client asked for. Lastro gives it that.

Claude Ship limits that matter for the design:

- It only works on the Team and Enterprise plans, and only with repositories on GitHub.
- It doesn't work with Zero Data Retention, with the HIPAA configuration or with customer-managed encryption keys.
- PR Steward and Claude Approvals are in beta.
- Usage is billed by tokens.

That is why **Lastro works on its own**, and Claude Ship comes in as an optional adapter (`lastro setup claude-ship`).

### `/ship` with Lastro

1. The developer runs `/ship` in Claude Code.
2. `/ship` pushes. Lastro's `pre-push` hook blocks the push if a touched requirement isn't verified. The agent gets the reason and fixes it first.
3. The PR opens. Lastro's CI publishes the "Lastro gate" check and writes the traceability block in the description.
4. If "Lastro gate" fails, **PR Steward** handles it like any broken check. The gate output separates:
   - **what the agent can fix**: a failing test, a condition with no run, a criterion with no test;
   - **what only a person can fix**: approval, preview, manual stage, a question for the client.

   For the second part, the output explicitly tells the Steward not to try and to tag a person.

### Code Review

`lastro export review-md` maintains a marked section in `REVIEW.md`, generated from:

- the glossary ("in the code, the role the client calls 'gerente' is `manager`");
- the invariants ("business rules and permissions are computed in the API");
- the layout contract ("only `app-modal`, `app-tabs`, `app-filter-bar`; no color outside the palette").

Code Review then reviews against the project's own rules, not just against general best practices.

### Claude Approvals

What Approvals can and can't read shapes the design:

- Approvals rules **don't read other checks** or CI results. "Lastro gate" doesn't enter the policy. It stays required in branch protection, next to the "Claude Approvals" check.
- A **custom classifier** (`repo/<name>`) reads the PR's title, description, changed files and diff, plus the files in its own folder. It doesn't read the rest of the repository.

Lastro uses this as follows:

1. CI writes the Lastro block in the PR description: requirements, acceptance criteria, reach and decisions.
2. A `repo/lastro_scope` classifier checks whether the diff stays within those requirements. This is what catches "controls that came in without anyone asking for them".
3. The policy requires a person for changes to the contract (`.lastro/**`) and to the paths the project marks as sensitive (money, permissions).

The PR description is text that the author can edit and that can try to influence the classifier. That is why the classifier is a support, and the firm lock is still the required "Lastro gate".

A draft generated by the adapter, always starting in observe mode. Before turning it on, review it with Claude Code's `claude-approvals` skill: an unknown key makes the whole file stop applying.

```yaml
# .claude/approvals.yml (draft)
version: 1
mode: observe
rules:
  - purpose: "Base: the author plus one more person. Claude approves when the review passes and the diff stays within Lastro's scope."
    paths: ["**"]
    verdict: { claude: comments, seats: 2 }
    override:
      - { if: "claude/code_review = pass AND repo/lastro_scope = pass", verdict: { claude: approves, seats: 1 } }
  - purpose: "The Lastro contract and the sensitive paths always need one person besides the author."
    paths: [".lastro/**", "src/billing/**", "src/permissions/**"]
    verdict: { claude: comments, seats: 2 }
  - purpose: "Review rules and classifiers: the author plus one more person."
    paths: ["**/.claude/**", "**/REVIEW.md", "**/.gitattributes", "**/.gitmodules"]
    nested: inherit
    verdict: { claude: comments, seats: 2 }
```

```yaml
# .claude/classifiers/lastro_scope/def.yml (draft)
version: 1
description: "Does the diff stay within the requirements listed in the Lastro block of the description?"
model: opus
prompt: |
  The PR description has a block between <!-- lastro:start --> and <!-- lastro:end -->
  with the requirements (id, statement, where, reach, acceptance criteria).
  pass: every behavior change visible in the diff is explained by one of those requirements.
  fail: the diff changes a behavior, screen, rule or permission that no requirement asks for,
  or the block doesn't exist. When in doubt, fail.
outputs:
  scope: { type: ordinal, values: [fail, pass] }
```

How the rules combine: the strictest one applies, and `seats: 2` means the author plus one more person. A PR that only touches ordinary code, with review and scope passing, needs only the author and can get Claude's approval. A PR that touches `.lastro/**` or `src/billing/**` always needs one more person.

## GitHub

- **Action** `lastro gate --ci`: runs the automatic stages in a clean environment, publishes the "Lastro gate" check with a table per requirement and updates the PR block.
- **Branch protection**: the adapter shows the steps to mark "Lastro gate" as required. Only a repository admin can do this.
- **Pinned PR comment**, optional, with the gate summary and links to the screenshots.

GitLab and others: the same command runs in any CI. The check and the PR block depend on an adapter.

## Test and analysis runners

Lastro doesn't know how to run tests in any language: it runs the project's command and reads standard formats.

| Format | Where it comes from |
|---|---|
| JUnit XML | Vitest, Jest, Playwright, pytest, PHPUnit, Pest, go test (via gotestsum), JUnit, RSpec |
| SARIF | ESLint, Semgrep, Ruff, PHPStan (with a formatter), CodeQL |
| LCOV, Cobertura | Coverage, optional and informational only |

Criteria are linked to tests by the case name in JUnit (`file::test name`), so it works on any stack that produces JUnit.

### Playwright

- The screenshots and videos attached to the report become Lastro artifacts, linked to the condition they ran under.
- Playwright's own visual comparison (`toHaveScreenshot`) can use the requirement's reference screen (`visual_ref`) as the baseline.
- The conditions in `lastro.yml` reach the tests through environment variables (`E2E_PROFILE`, `E2E_THEME`, `E2E_ZOOM`). Each project decides how its tests use each one.

## Project knowledge tools

Lastro holds the contract of **one repository**. Tools that bring several projects together can read `.lastro/` and the history through the CLI (`lastro export --json`) to provide a cross-project view or a client portal. The first planned integration is Loqivo.
